# WAGO PFC200 750-8212 — the target controller

Surveyed 2026-08-19, the day it came online. This is the machine ROADMAP
Milestone 4 and `deploy/systemd/README.md` call "a dedicated machine next to
the coupler" — except it would not be next to the coupler, it would **be** the
coupler. The direction is the owner's (BACKLOG, 2026-08-06: "the whole control
on the PFC200"); the sequencing is proposed in BACKLOG and not yet decided, so
there is no D-entry to cite yet.

Credentials, host key and the MQTT accounts are in `docs/PFC200.local.md`,
which is git-excluded. Nothing secret belongs in this file.

## What runs on this box

| container | what it is | if it dies |
|---|---|---|
| `heatctl` | the control core (PID 1) + the optimizer backgrounded beside it | the container dies with it and Docker restarts it; the coupler watchdog zeroes the outputs after 10 s |
| `mqtt-broker` | mosquitto: control plane, sensors, bridge to HA | heatctl keeps controlling on return-temperature fallback and default setpoints |
| `normaliser` | Shelly topics → retained, expiring, bare floats (D-047) | affected rooms age out and fall back to house-average control |
| `journal` | the black box: every message onto the SD card | nothing, except that the next incident has no record |

`docker ps` on the device is the fast check; each has a `run-*.sh` in
`/media/sdcard/docker-root/<name>/` and a matching `deploy/pfc200/` script in
the repository. Only `heatctl` has a deploy that can interrupt control — see
the cutover procedure below.

### The plan, revised 2026-08-24

The A–E ladder no longer describes this well. Two of its assumptions died on
2026-08-24: E's blockers are gone (the KBUS is free and the ABI is documented),
and D stopped needing a CODESYS program. What is left is **one physical swap
with two possible things talking to the terminals afterwards**.

**D is the near-term target, and the reason is the failsafe.** Native KBUS
removes the Modbus watchdog, which is today the only failsafe that survives
heatctl dying entirely — and nothing yet replaces it. Going to Modbus-on-the-box
first **keeps that watchdog**, so the swap can happen now and the failsafe
question travels with E, where it belongs. Owner, 2026-08-24: defer it to when
E is actually implemented; that is what makes D a useful step rather than a
detour.

What the swap buys immediately: the module stack moves onto the PFC, so
**Modbus stops crossing the network** — the standing risk since 2026-08-08 —
and the manifold wiring can be finished and the cabinet closed. The wiring is
identical for D and E; only the protocol above it changes later.

**THE GATING CHECK, and it is not optional.** `pfc-modbus-server` emulates a
**750-362** register map; ours is a **750-352**. Two things must be verified on
the bench *before* the swap is scheduled:

1. **Does it implement the coupler watchdog at `0x1000+`?** If it does not, D
   silently loses the failsafe too and is no longer the safe step it looks
   like — at which point the failsafe question is back and D's rationale is
   gone. This is the single most important thing to establish.
2. **Do our register offsets hold?** `docs/HARDWARE.md` has input registers
   12–27 and holding 12–27 for the 352. Same family and probably the same
   process-image rules, but "probably" is not good enough for the thing the
   plant is standing on with the cabinet open.

**CORRECTION, tested the same day: they are NOT answerable on an empty rail.**
I claimed they were. Pulling `wagoautomation/pfc-modbus-server` (55 MB, four
years old) and starting it against the bare PFC:

  * it **does** start and listen on 502, with the runtime off;
  * but the KBUS will not initialise — `!!!! KBUS ERROR: 3`, repeating;
  * and **every** register read returns Modbus exception **6, slave device
    busy** — holding and input, process image and `0x1000` alike. Not
    exception 2, which would have told us a register does not exist.

So the emulated map cannot be probed until terminals are present. The
verification has to happen **on swap day**, which is fine as long as it is
staged — see below.

Two things were learned without hardware, though:

**The watchdog exists.** `strings` on `kbusmodbusslave` shows `Watchdog Init`,
`Watchdog start/stop/trigger`, `ModbusWatchdog Expired Task`, `MODBUS Watchdog
expired`, `Watchdog Timeout: %ums`. So D does keep a coupler-style watchdog,
which is the premise the whole plan rests on. **What it does on expiry is still
unknown** — no string suggests the direction, so that is a bench observation,
not a documented fact.

**Its failure mode is the right one.** With the KBUS dead it answers *busy*
rather than hanging or returning stale zeros. heatctl's `modbus_direct` would
see exceptions, fail its reads, and fall into the stale-data failsafe — which
is correct behaviour, and the same shape as the intermittent 750-352 faults
already seen on 2026-08-22.

Its shipped config is also worth knowing:

```
modbus_port 502        max_tcp_connections 5     operation_mode 0   (async)
modbus_delay_ms 0      kbus_priority 60          kbus_cycle_ms 50
```

**A 50 ms KBUS cycle** — which matters well beyond this phase, because the
planned 100 ms DHW fast loop (Milestone 2) needs to fit inside it, and it does.

### Stage the swap, because the checks need terminals

Move **one 750-559 first**, verify against it, then move the rest:

1. one analog-output module onto the PFC, rail otherwise empty;
2. confirm the KBUS initialises and registers answer instead of returning busy;
3. read back the holding registers and find where those four channels landed —
   that settles the 362-vs-352 offset question against real hardware;
4. trip the watchdog and watch which way the outputs go — that settles C3 and
   the open 2026-07-31 contradiction;
5. only then move the remaining eleven terminals.

Costs four valve channels for the duration, on a plant that is down anyway, and
turns "commit and hope" into a bounded test with the 352 an arm's length away.

### What the swap actually found, 2026-08-24

**The register map is identical to the 750-352's.** The server enumerates the
rail on start and logs it — read that log rather than guessing:

```
Pos:1  16DI       BitOffsetIn:448  (16 bits)      -> word 28
Pos:2  750-652    In/Out 0, 192 bits              -> words 0-11
Pos:3-6  4x750-463  BitOffsetIn 192/256/320/384   -> INPUT   regs 12-27
Pos:7-10 4x750-559  BitOffsetOut 192/256/320/384  -> HOLDING regs 12-27
Pos:11-12 2x 2DO   BitOffsetOut 448, 450          -> coils
```

Bit offset 192 / 16 = word 12, four modules of four words each = 12–27, on both
sides. Exactly what `docs/HARDWARE.md` records for the 352, so heatctl needed
**nothing but an address change**.

**The watchdog is live**, which was the premise of going this way. It accepts
our Standard-style write-only mask and heatctl's per-cycle valve write
retriggers it, as on the 352:

```
heatctl:       coupler watchdog armed: 10.0 s, mask 0x8020 (FC6+FC16)
registers:     0x1000 = 100 (10.0 s)    0x1001 = 32800 (0x8020)
modbus-server: 13629 x "Watchdog trigger"
```

**Three caveats, none of them blocking:**

- **`WD_STATUS` at `0x1006` always reads 0**, even while the watchdog is being
  triggered thousands of times. The 362 emulation does not report status
  there. Effect: heatctl never sees ACTIVE, so it re-arms every cycle and logs
  "armed" every second. Harmless, but its model of the watchdog is wrong.
- **Holding registers alias to the INPUT image on read.** Reading holding
  12–15 returns the PT1000 values while heatctl is commanding 0. So
  `valve_readback` is meaningless here — heatctl auto-disables it, which is the
  right degradation, but that check is gone.
- **Expiry direction is still unknown.** It cannot be observed through the
  registers because of the aliasing, so it needs a physical look at whether a
  valve moves when writes stop. This is the last open piece of C3 and of the
  2026-07-31 contradiction.

### ⚠ THE SD CARD DOES NOT COME BACK BY ITSELF

**Read this before touching the card or rebooting.** Found the hard way during
the swap, and it takes the plant controller out silently.

The card was knocked out of its slot while the unit was being handled. On
reinsertion and reboot, **WAGO's hotplug automounter claimed it and mounted it
by UUID** at `/media/<uuid>` instead of the `/etc/fstab` entry for
`/media/sdcard`. Docker's `data-root` is `/media/sdcard/docker-root`, where a
244 MB **tmpfs fallback** sits — so dockerd started on an empty root with **no
images, no containers and no plant controller**, and looked perfectly healthy
doing it.

```sh
# the symptom
mount | grep mmcblk0
  /dev/mmcblk0p1 on /media/bf594745-2a89-4f55-bf1d-0d9c5a571e85 type ext4
df -h /media/sdcard        # 244 MB tmpfs, ~0 % used
docker ps                  # empty

# the recovery, in this order
/etc/init.d/dockerd stop
umount /media/sdcard/docker-root          # the tmpfs shadowing the real path
umount /media/<uuid>
mount /media/sdcard                       # per fstab
ls /media/sdcard/docker-root              # expect 16 entries
/etc/init.d/dockerd start                 # --restart always brings all four back
```

Nothing was lost — configs, the `*.env` files holding on-device-generated
broker credentials, and all four journal files including a 253 MB live one.
But the failure mode is the dangerous kind: **everything reports healthy and
the plant simply has no controller.**

### Swap-day sequence

1. Compressor off first, watched to 0 Hz. Er03 does not reliably self-clear.
2. Move terminals 1–12 and the 750-600 from the 352 onto the PFC.
3. Verify the process image against `docs/HARDWARE.md` before trusting it —
   16 PT1000 in, 16 analog out, 1:1 with the circuit numbers. A wrong offset
   shows up as the wrong valve moving.
4. Point heatctl's `HEATCTL_MODBUS_HOST` at the local server, bring it up.
5. Run the watchdog trip test: stop writing, confirm the outputs move, record
   **which way** — that settles the open 2026-07-31 direction contradiction.

Rollback is physical and quick: the 352 goes back on the rail with its own
address. Keep it on the shelf, configured, until E is done.

**What B bought, and what it did not.** The control plane is now entirely
on-box: heatctl talks to `mqtt-broker` over the internal `plc` docker network,
so losing the LAN no longer costs it commands, telemetry or room sensors that
publish here. Modbus to the coupler still crosses the network — that is what D
removes, and it is why the 2026-08-08 switch incident is still a live risk.

Rollback is two commands: stop the container, `ha addons start local_heatctl`.
The App is stopped rather than removed for exactly that reason.

**Unproven so far:** whether one ARMv7 core holds the 1 s loop under sustained
load, and how Docker-on-SD wears. Both were the point of doing B before D.

## Modbus TCP and the watchdog — the question that gates the swap

`BACKLOG.md` (2026-07-31) made the whole migration conditional on one thing:

> **does the PFC200's Modbus server offer an equivalent output-zeroing
> watchdog?** […] If the answer is yes, the swap is a day.

**Partially. There is a watchdog, and it looks like the wrong kind.**

`/etc/config-tools/modbus_config` configures the Modbus service without
CODESYS. Read 2026-08-19:

```
tcp.enabled  = true      udp.enabled = true
tcp.port     = 502       udp.port    = 502
alternative-watchdog.enabled = false
alternative-watchdog.timeout = 0
alternative-watchdog.options = 4
```

Three things follow, and the middle one is the problem.

1. **A Modbus server is configurable natively.** CODESYS is not required to
   turn it on. Good — the BACKLOG's bad branch ("the whole toolchain is on the
   critical path") is not forced.

2. **The only watchdog on offer is called "alternative", and D-004 chose
   *Standard* on the 750-352 specifically to avoid that behaviour.** Standard
   evaluates a coding mask, so restricting it to `0x8020` (FC6 + FC16) makes
   "watchdog satisfied" mean *outputs are being driven* — which is why
   heatctl needs no separate heartbeat, its per-cycle valve write **is** the
   heartbeat. Alternative resets on any telegram, which D-004 calls "exactly
   backwards": a heatctl that is reading fine but failing to write would keep
   the watchdog fed while the outputs went stale.
   There **is** an `options` mask, currently 4, so the semantics may be
   configurable back toward Standard. **Unverified — this is a hypothesis
   about a name, and names are hypotheses.** Bench-test it before relying on
   it, exactly the way the 750-352's trip test was run on 2026-07-26.

3. **Nothing is listening on 502 today**, because the Modbus server lives
   inside the PLC runtime and no runtime is selected: `get_runtime_config`
   returns empty, `get_possible_runtimes` offers `0 1`, and no CODESYS process
   is running. `/home/codesys/` exists (`CODESYSControl.cfg`, `PlcLogic`) so
   the runtime is installed, just inert.

## The other route: no Modbus at all

`/dev/kbus0` exists and the WAGO DAL libraries are present — `libdal.so`,
`libIoDrvDal.so`, `libIoDrvKbus.so`, `libdbuskbuscommon.so`. So a Linux process
on this box can reach the process image **directly**, with no Modbus server, no
runtime and no CODESYS.

That is what `IOBackend` in `heatctl/backends/base.py` was built for: a third
backend beside `modbus_direct` and `mqtt_io`, and the one where the control↔I/O
link stops crossing a network at all. The 2026-08-08 switch incident — both
Modbus endpoints lost together to a broadcast storm — is the argument for it.

**No SDK headers are on the device** (`find / -name "dal*.h"` is empty), so this
route needs WAGO's SDK or a documented ABI, and it is not a weekend. It is the
better destination, not the first step.

### The DAL is reachable from heatctl's own container — verified 2026-08-24

The biggest unknown in Phase E was whether a Debian container could drive
WAGO's PTXdist-built libraries at all. It can, and the recipe needs no
compiler, no SDK on the device, no new dependency and no change to the base
image:

```python
G = ctypes.RTLD_GLOBAL
for dep in ("libffi.so.8", "libglib-2.0.so.0", "liblibloader.so.0"):
    ctypes.CDLL(f"/hostlib/{dep}", mode=G)      # absolute path, in order
lib = ctypes.CDLL("/hostlib/libdal.so.1.0.1", mode=G)
lib.adi_GetApplicationInterface.restype = ctypes.c_void_p
lib.adi_GetApplicationInterface()               # -> 0xb6564154, non-NULL
```

run as

```sh
docker run --device /dev/kbus0 \
  -v /usr/lib:/hostlib:ro -v /usr/lib/dal:/usr/lib/dal:ro  python:3.12-slim ...
```

**NEVER put `/hostlib` on `LD_LIBRARY_PATH`.** The first attempt did, and the
container's own Python then bound to the host's glibc and died:
`/hostlib/libc.so.6: version GLIBC_2.38 not found (required by
libpython3.12.so)`. Host glibc is **2.35**, the container's is **2.41**, and
only that direction works - a 2.35-built library runs fine on 2.41, not the
reverse. So preload the host's dependencies by absolute path with
`RTLD_GLOBAL`, which satisfies `libdal`'s `DT_NEEDED` entries from within the
namespace, and leave the search path alone.

`/usr/lib/dal/` must be mounted at that exact path, because `libdal` loads its
device libraries from there by name.

**The architecture**, for whoever writes the backend: `libdal.so` exports
exactly one symbol, `adi_GetApplicationInterface`, and is a thin loader over
`liblibloader`. Everything else is a struct of function pointers it returns -
so the ABI is a **vtable layout, not a symbol list**, and cannot be recovered
from `nm`. The device libraries live in `/usr/lib/dal/`: `libpackbus.so` is
KBUS (it opens `/dev/kbus0` and `/dev/ttyKbus`), alongside `libmbs.so`
(Modbus slave), `libcanopen*`, `libbacnet`, `libdps`.

**The ABI is documented by WAGO and the header exists** - found 2026-08-24, so
this is no longer a blocker. In `github.com/WAGO/pfc-howtos`:

| what | where |
|---|---|
| the official manual | `HowTo_ADI-MyKBusApplikation/a800010_en - ADI-DAL for PFC firmware 11 patch 2.pdf` |
| every ADI function | `.../src_kbusdemo/adi_functions.txt` |
| a working KBUS app | `.../src_kbusdemo/kbusdemo.c` |
| the header itself | `<dal/adi_application_interface.h>`, in the SDK |

The call sequence, from WAGO's own demo:

```c
adi = adi_GetApplicationInterface();
adi->Init();  adi->ScanDevices();
adi->GetDeviceList(sizeof(list), list, &n);       // find DeviceName "libpackbus"
adi->OpenDevice(id);  adi->SetApplicationState(RUNNING);
// per cycle: CallDeviceSpecificFunction("libpackbus_Push", ...)
//            ReadStart/ReadBytes/ReadEnd, WriteStart/WriteBytes/WriteEnd
```

`libpackbus.h` (in `libpackbus.tgz` in the SDK) names the device-specific
functions: `libpackbus_Push`, `libpackbus_get_terminal_info_32`,
`libpackbus_get_kbus_status`, `libpackbus_get_kbus_timing`. Those are strings
passed to the ADI, not exported symbols - which is why `nm` on the library
shows nothing useful.

**Note the demo runs the KBUS loop at `SCHED_FIFO` priority 40.** On this
PREEMPT_RT kernel that is presumably how cycle jitter is kept sane, and a
Python implementation would want `os.sched_setscheduler` to match. Untested.

Do NOT guess the struct layout. It is a vtable behind a function pointer in
the I/O path; a wrong offset is memory corruption, not an exception.

### Why Phase D needs a CODESYS application — measured 2026-08-24

`modbus_config get tcp enabled` returns **true** on port **502**, and nothing
has ever listened there. Starting CODESYS3 (`config_runtime -w
runtime-version=1`) brought up port 11740, the CODESYS gateway, but **not 502**,
with `get_codesys_application_info -j` returning `{}` - no application loaded.
There is no `modbus` daemon, no `modbus` init script and no modbus binary on
the box; what exists is `/usr/lib/dal/libmbs.so`, a **DAL device library**.

So the Modbus server is an ADI device that an application instantiates, and
`modbus_config` sets parameters for something that does not exist until one
does.

**AMENDED THE SAME DAY: that does not have to be a CODESYS application.** WAGO
publish `github.com/WAGO/pfc-modbus-server` - a Docker image wrapping a
`kbusmodbusslave` daemon that serves Modbus TCP straight off the KBUS, and
whose own setup script sets `runtime-version=0`. So it runs with CODESYS
*off*, which is the opposite of what I concluded an hour earlier from the
absence of a listener on 502. Recorded because the wrong version was nearly
acted on.

What it costs, and none of it is free:

- **`--privileged`**, plus the D-Bus system socket mounted in.
- **A prebuilt 24 KB armhf `.ipk` with no source.** Vendor-published rather
  than a hobbyist's, which is better provenance than `pfc-kbus-api` - but last
  pushed 2022-06-30.
- **The register map emulates a 750-362, not our 750-352.** Same family and
  probably the same process-image rules, but `docs/HARDWARE.md`'s offsets
  (input regs 12-27, holding 12-27) must be **verified, not assumed**.
- **A fragile bootstrap**: WAGO's own README says if the KBUS fails to init,
  "stop container, activate runtime, deactivate runtime, start container".
  That is a reboot-order trap waiting to happen on a plant controller.
- **The physical RUN/STOP switch gates it** - STOP means no Modbus server.

So Phase D is cheaper than "write a PLC program", and still carries a closed
binary and a privileged container in the I/O path.

### Releasing `/dev/kbus0` from CODESYS

The runtime holds the device node while it runs — measured 2026-08-21,
`fuser /dev/kbus0` returned PID 2366, `/usr/bin/codesys3`, also costing ~18 % of
the only core. WAGO's own config tool switches the runtime off, and it is
reversible:

```sh
/etc/init.d/runtime stop
/etc/config-tools/config_runtime -w runtime-version=0            # runtime: none
/etc/config-tools/config_runtime cfg-version=3 webserver-state=disabled
# and back:
/etc/config-tools/config_runtime -w runtime-version=3
/etc/config-tools/config_runtime cfg-version=3 webserver-state=enabled
```

**Verified 2026-08-24, not merely inferred:** after `runtime-version=0`,
`fuser /dev/kbus0` reports the node FREE, `codesys3` is gone from the process
table, and its ~18 % of the single core comes back. Note this box offers only
`0 1` - **0 = None, 1 = CODESYS3**. The kbus-api script used `runtime-version=3`
(e!Runtime), which this firmware does not support, so copying it verbatim would
have failed.
**Prefer this to disabling `/etc/rc.d/S98_pp_codesys3`** — it is what the
vendor tooling is for and it has a documented undo. Source: the setup scripts
of `jessejamescox/pfc-kbus-api`, whose own MQTT-bridge approach is rejected for
this project (see BACKLOG); the procedure is the useful part.

**Unresolved, and it matters because Phase E's blocker is stated in terms of
it:** the 2026-08-19 survey recorded `get_runtime_config` empty and no CODESYS
process at all, yet on 2026-08-21 it was running and holding the node. Both
cannot be true. Find out which before planning around either.

## Mosquitto

Runs as a Docker container `mqtt-broker`, recreated 2026-08-19 from
`/media/sdcard/docker-root/mosquitto/run-broker.sh` — a script rather than a
remembered `docker run`, with the **image pinned by digest** rather than
`:latest`. An unpinned tag means a pull can change the broker under a working
plant, which is the same trap as an unpinned `requirements.txt`.

Config, certs, data and log are bind-mounted from
`/media/sdcard/docker-root/mosquitto/`, so nothing the broker keeps lives
inside the container.

```
allow_anonymous false
persistence true                 # verified: "Restored 2 retained messages"
listener 8883                    # TLS, own CA. The ONLY published port.
listener 1883                    # container network `plc` only, NOT on the host
```

**8883 is the only port exported to the LAN.** 1883 stays on the internal
`plc` docker network for heatctl, which has no TLS support in `mqtt_plane.py`
— so its credentials never cross the wire and it pays no TLS cost on a single
ARM core for traffic that never leaves the box. The 9001 mapping is gone; it
pointed at a listener that did not exist.

Three accounts, each able to write only what it owns:

| user | write | read |
|---|---|---|
| `heatctl` | `heatctl/#`, `homeassistant/#` | `heatctl/#`, `roomtemp/#`, `rtl_433/#`, `sensors/shellies/#` |
| `homeassistant` | `heatctl/set/#`, `heatctl/hp/set/#`, `heatctl/env/#`, `roomtemp/#` | `heatctl/#`, `homeassistant/#`, `sensors/shellies/#` |
| `shelly` | `sensors/shellies/#` | — |

HA deliberately **cannot write heatctl's state topics**. A stale retained value
on `heatctl/temp/...` would be indistinguishable from a live measurement, which
is the failure shape this project keeps meeting. Verified by publishing to each
topic and checking what actually landed — `mosquitto_pub` reports success even
when the broker silently drops on ACL denial, so its exit status proves nothing.

**Permissions gotcha, cost an outage during setup:** `docker exec id` reports
root, but the eclipse-mosquitto entrypoint drops the *main process* to uid
**1883**. Tightening the bind-mounted files to root-owned 0600 made them
unreadable and the broker crash-looped on `Unable to open pwfile`. They are now
owned `1883:1883` with 0600/0700. mosquitto 2.1 also warns that a future
version will refuse a passwd file not owned by root — those two requirements
will collide, and the answer is probably to stop bind-mounting secrets.

Still open: the CA private key was moved off the device to the workstation
(`docs/PFC200.local.md`), so the broker can no longer issue certificates it
presents — but it also means renewals happen off-box.

## The bridge to Home Assistant

Built 2026-08-19. Config in `deploy/pfc200/bridge.conf.template`; the live copy
on the device carries the credential and is 0600 in `config/bridge.d/`.

```
out:  heatctl/#   homeassistant/#   sensors/#
in:   rtl_433/…/WH65B/210/temperature_C     permanent (outdoor contingency)
      rtl_433/…/WH32/245/temperature_C      until Arbeitszimmer gets a Shelly
      heatctl/set/#   heatctl/hp/set/#      dashboard commands
      roomtemp/#   heatctl/env/dew_point    TRANSITIONAL - delete when done
```

Hosted on the PFC rather than on HA deliberately: this side's configuration is
version-controlled, HA's broker configuration is the un-versioned thing
`docs/HA_INTEGRATION.md` exists to compensate for.

**It is a transport change, not an independence gain.** While a room's sensor
still reaches heatctl through HA, that room still depends on HA. What the
bridge buys is that the two migrations — compute onto the PFC, sensors onto
this broker — can happen in either order and one room at a time.

**Narrowed on purpose.** The first version bridged `rtl_433/#` wholesale and
imported 625 retained topics, most of them fossils from 2022. See below; that
is why the inbound leg names two exact topics.

## Retained fossils, and what they were hiding

Bridging `rtl_433/#` pulled a **2022 retained `events` message** onto the PLC
broker, carrying `temperature_C: 13.4` on the very topic that feeds the slab
target — where `UA_ao*(T_set-AT)` makes outdoor the largest single term.

Worse, restarting HA's Mosquitto **replayed that fossil into Home Assistant**,
and `sensor.fineoffset_wh65b_210_t` took it as current: 13.4 °C, last reported
at the moment of the restart, against a genuine 17.3 half an hour earlier.

Which exposed the thing underneath: **the WH65B had gone silent** around
19:34 UTC and the retained fossil was masking it. A dead sensor looked alive
because a broker was remembering 2022 on its behalf. This is the concrete form
of the hazard in "Retained sensor data and staleness detection" in BACKLOG —
retain defeats arrival-time staleness, and here it defeated a human's ability
to notice too.

All retained `rtl_433/#` topics were cleared on both brokers (625 on HA, mostly
years of decoded radio noise from neighbours' meters). Live publishers
repopulate what is live; nothing else should be remembered.

**heatctl was insulated**, and by accident this validated the three-tier
outdoor design: `sensor.heatctl_outdoor_source` reads `forecast`, so the plant
never used either the fossil or the dead station.

## Cutover procedure — and why the source goes off first

heatctl now runs here (2026-08-20). Moving control between machines means a
gap, and the gap is what bites.

**Stop the source first.** When the controller stops, the coupler watchdog
expires after 10 s and zeroes the outputs. The actuators are NC, so they close.
Flow through the heat pump collapses. A *running* compressor then trips
**Er03**, its water-flow fault, which latches — and the unit shuts its own
water pump down with it, so restored flow cannot clear it by itself.

Learned by doing it wrong: the first cutover left the plant unmanaged for about
90 seconds while a missing script was copied across, and Er03 latched eleven
seconds after the new controller started reading fault registers. It cleared itself after
4.5 minutes, matching three self-clears on 2026-08-10.

**Do not read that as tolerance.** Owner: *"Er03 is self clearing if the cause
goes away immediately. It backs off and eventually gets stuck."* The self-clear
is the early part of a retry sequence with a lengthening backoff, so every trip
spends a budget nobody can read and makes the next one likelier to latch for
good — at which point it needs someone on site. See `docs/HEATPUMP.md`.

```
1. Note the current mode.
2. heatctl/set/mode -> off      and WATCH the compressor reach 0 Hz.
3. Stop the losing controller.  ha addons stop local_heatctl
4. Start the winning one.       deploy/pfc200/deploy-heatctl.sh  (SOURCE_STOPPED=1)
5. Restore the mode from step 1.
```

Steps 3 and 4 should still be close together — the valves close either way and
the rooms notice eventually — but with the compressor already off, a slow
step 4 costs comfort rather than a latching fault.

**Single writer.** The App must be *stopped*, not idle. `deploy-heatctl.sh`
checks this from the workstation, which can reach both machines, and fails
closed if it cannot tell.

## The Shelly that already publishes here

`shellyhtg3-9070695AA90C` at `192.168.178.72`, base topic
`sensors/shellies/wohnzimmer`, TLS on 8883 as user `shelly`.

```
sensors/shellies/wohnzimmer/status/temperature:0   {"id":0,"tC":23.7,"tF":74.6}
sensors/shellies/wohnzimmer/status/humidity:0      {"id":0,"rh":62.9}
sensors/shellies/wohnzimmer/online                 true | false     (LWT, retained)
sensors/shellies/wohnzimmer/events/rpc             NotifyFullStatus, NotifyEvent
```

This is a **different device** from the four H&T G3 already in HA. Note the
payload is JSON, not the bare number heatctl's `room_temp_topic` currently
expects — the rtl_433 room reads a bare float. A JSON-extracting topic form is
needed either way.

**Two measured problems with the direct path, both about staleness:**

1. **`wakeup_period` is 600 s and the device deep-sleeps**, despite
   `devicepower:0.external.present = true`. It connects, publishes, disconnects,
   every six minutes observed. Against `room_temp_max_age_s: 900` that leaves
   one missed wake of slack.
2. **Only `online` is retained.** Subscribing while the device sleeps returns
   `online false` and *no temperature*. So a heatctl restart can sit up to a
   full sleep period with no reading for that room and fall back to
   house-average control — silently, which is the failure shape
   `docs/HA_INTEGRATION.md` risk 2 already tracks.

The HA-bridged siblings avoid this with a `/2` heartbeat automation. A
device-direct Shelly has no such helper, which is the honest cost of removing
HA from the path.

**SLEEP CANNOT BE DISABLED, and the reason is physical** (owner, 2026-08-20):
an always-on CPU self-heats and distorts the temperature reading. The device is
accurate *because* it powers down between samples. So "keep it awake" is not a
setting anyone forgot — it is closed permanently, and two mitigations that
depended on it are closed with it:

- **`online` cannot gate freshness.** It is false roughly 357 s in every 360 by
  design. It survives only as a *wake event marker*.
- **Payload timestamps cannot either.** The clock is unset right after wake
  (`"unixtime":null`), which is precisely when a first-message-after-reconnect
  would need it.

What remains is that **room temperature is a sampled signal**, and the design
has to hold that rather than work around it. **The period is 360 s, measured**
(the normaliser's first two intervals were 360 and 358) — not the
`wakeup_period: 600` the device reports, which is worth knowing before sizing
anything against it.

That is what `normaliser` below is for.

Also: do not mount these where air exchange is poor or near a heat source. The
accuracy depends on the CPU being off.

## The normaliser (container `normaliser`)

Live since 2026-08-20. Full argument in **D-047**; module docstring in
`normaliser/main.py`. What an operator needs on this page:

**What it does.** Subscribes the raw Shelly topics, republishes each sample to
`sensors/room/<room>/…` as a **bare float, retained, with an MQTT 5
message-expiry** equal to heatctl's `room_temp_max_age_s`. The broker then owns
the deadline: it serves the value only while it is young enough, decrements the
remaining interval as it sits there, and deletes it when it runs out —
persisted across a broker restart. heatctl reads it as a v3.1.1 client and
needed no code change.

    sensors/room/<room>/temperature_c   bare float, retained, expiring
    sensors/room/<room>/humidity_pct    bare float, retained, expiring
    sensors/room/<room>/sample_ts       unix seconds at receipt
    sensors/room/<room>/interval_s      seconds since the previous sample
    sensors/room/<room>/max_age_s       freshness window, from the device

**What it deliberately is not.** No Modbus library, no `heatctl/` package, no
route to the coupler or the heat pump — it cannot touch the plant whatever it
is asked to do. Its own broker account (`normaliser`, write `sensors/room/#`
only), because heatctl must not be able to write the topics it reads as
measurements.

**Deploy.** `deploy/pfc200/deploy-normaliser.sh` from the repository root.
Unlike the heatctl deploy this needs **no `SOURCE_STOPPED`, no peer check and
no compressor care**: restarting it cannot create a control gap. Config lives
at `/media/sdcard/docker-root/normaliser/config.yaml` and, as always, a deploy
ships code and never config. The broker credential is in
`normaliser.env` beside it (see `docs/PFC200.local.md`).

**Checking it.** Logs are quiet by design — a line when a room first appears or
returns after its value had expired, and nothing for the routine six-minute
cadence. To see the tree and how much life each value has left:

    docker run --rm --network plc eclipse-mosquitto \
      mosquitto_sub -h mqtt-broker -p 1883 -u heatctl -P "$PW" \
      -v -W 3 -t 'sensors/room/#'

A room that has gone quiet **disappears** from that listing rather than showing
a stale number. That is the intended alarm.

**Known limit.** The expiry property does not survive the v3.1.1 bridge, so on
Home Assistant's broker these are ordinary retained values that never expire.
`sample_ts` is published for exactly that reason — on the HA side it is the
only staleness signal there is, and anything built on this tree must use it.

## The black box (container `journal`)

Live since 2026-08-21. Argument in `journal/main.py`; what an operator needs:

**What it does.** `mosquitto_sub -t '#' -F '%U %t %p'` piped into a small
Python rotator. Every message on the broker, timestamped at receipt, appended
to `/media/sdcard/docker-root/journal/data/mqtt-YYYYMMDD.log`. Rolls at UTC
midnight, gzips the closed day, prunes past `JOURNAL_RETAIN_DAYS` (90).

    1787313600.123 heatctl/capacity/reason margin -1.00 K low, waiting

**Why it exists.** The 2026-08-21 cooling investigation was only possible
because somebody happened to be sampling six topics by hand; an earlier ramp
the same morning left no record at all. heatctl's SQLite history is not a
substitute - it stores what heatctl *models*, once a minute, and the question
that mattered was what the frequency ceiling did between two raises.

**Why the subscriber is C.** The first version used aiomqtt and **lost about
40 %** - 1496 records against roughly 2500 published in the same minute, with
mosquitto logging `Outgoing messages are being dropped for client journal` and
eventually evicting it. `mosquitto_sub` alone kept up completely at lower CPU.
One ARMv7 core with no idle time does not forgive per-message work in Python.
The Python half now only rotates, compresses and prunes, and the pipeline
records everything: **2376 against 2366** seen by an independent subscriber
over the identical wall-clock window.

**Measuring it, if you ever need to.** Do NOT compare against a freshly
connected `mosquitto_sub | wc -l`. A new subscriber receives the **retained
snapshot** first - 809 messages here - which a long-running recorder never
sees, so the recorder looks about 25 % short when it is losing nothing. That
artifact cost two rounds of chasing a bug that was not there. Compare by
wall-clock window instead:

    # subscriber side, with timestamps
    mosquitto_sub ... -F '%U %t' -W 130 -t '#' > /tmp/w.txt
    # then count both over the same seconds
    awk '$1>=<start> && $1<<end>' /tmp/w.txt | wc -l
    awk '$1>=<start> && $1<<end>' .../mqtt-YYYYMMDD.log | wc -l

**Why it is deprioritised rather than capped.** `--cpu-shares 128`, and no
`--cpus`. The first attempt used a hard `--cpus 0.10` ceiling and silently
dropped two thirds of the traffic. Shares bind only under contention, and then
heatctl at the default 1024 wins the core 8:1.

**Reading it.**

    ssh root@192.168.178.62
    D=/media/sdcard/docker-root/journal/data
    grep " heatctl/capacity/reason " $D/mqtt-20260821.log      # today
    zgrep " heatctl/hp/silent_max_freq_cooling_hz " $D/*.gz    # history

Timestamps are epoch seconds; `date -d @1787313600` converts. A
`journal/started` record marks each restart, and a gap in the timestamps is the
outage - there is no health topic to go stale.

**Size.** Roughly 5.7 KB/s of records, compressing about 10:1 on roll, so tens
of MB per archived day against 110 GB free. Retention is the only thing worth
tuning, and the card is the least scarce resource on this machine.

**It cannot touch the plant.** No Modbus library, no `heatctl/` package, and
the `journal` broker account has `topic read #` and **no write rule at all** -
`tests/test_journal.py` asserts the absence.
