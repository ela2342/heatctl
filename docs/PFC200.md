# WAGO PFC200 750-8212 — the target controller

Surveyed 2026-08-19, the day it came online. This is the machine ROADMAP
Milestone 4 and `deploy/systemd/README.md` call "a dedicated machine next to
the coupler" — except it would not be next to the coupler, it would **be** the
coupler. The direction is the owner's (BACKLOG, 2026-08-06: "the whole control
on the PFC200"); the sequencing is proposed in BACKLOG and not yet decided, so
there is no D-entry to cite yet.

Credentials, host key and the MQTT accounts are in `docs/PFC200.local.md`,
which is git-excluded. Nothing secret belongs in this file.

## Status

| phase | | |
|---|---|---|
| A | broker: account, ACL, persistence, TLS-only on the LAN, pinned image | **done** 2026-08-19 |
| — | bridge to Home Assistant, both directions | **done** 2026-08-19 |
| — | Wohnzimmer piloted onto a Shelly publishing here direct | **done** 2026-08-19 |
| B | heatctl itself, containerised on this box | **done** 2026-08-20 |
| C | bench the Modbus watchdog — **gates D** | not started |
| D | swap the 750-352 coupler for this unit | blocked on C |
| E | native KBUS backend, retiring Modbus from the control path | later |

**What B bought, and what it did not.** The control plane is now entirely
on-box: heatctl talks to `mqtt-broker` over the internal `plc` docker network,
so losing the LAN no longer costs it commands, telemetry or room sensors that
publish here. Modbus to the coupler still crosses the network — that is what D
removes, and it is why the 2026-08-08 switch incident is still a live risk.

Rollback is two commands: stop the container, `ha addons start local_heatctl`.
The App is stopped rather than removed for exactly that reason.

**Unproven so far:** whether one ARMv7 core holds the 1 s loop under sustained
load, and how Docker-on-SD wears. Both were the point of doing B before D.

## What it is

| | |
|---|---|
| Order number | 750-8212 (PFC200 G2, 2×ETH) |
| OS | PTXdist 2024.12.0, WAGO firmware |
| Kernel | 6.6.94-**rt56 PREEMPT_RT**, armv7l |
| CPU / RAM | **1 core**, 500 MB (488 MB visible to Docker) |
| Internal eMMC | 8 GB — root fs is **283 MB with 88 MB free** |
| `/home` | 1.4 GB, 1.1 GB free |
| SD card | 119 GB (`mmcblk0p1` → `/media/sdcard`), 110 GB free |
| Docker | 25.0.4, overlay2, root dir **on the SD card** |

Two numbers to keep in mind before planning anything: **one core**, and a root
filesystem with 88 MB free. Nothing installs to `/`. The real-time kernel is a
genuine asset for the planned 100 ms DHW loop — the HA host has no such
guarantee.

**There is no Python on this device**, and no pip — only `opkg` against WAGO's
feed. So heatctl runs here in a container or not at all; `deploy/systemd/`
does not apply. That is a platform fact, not a preference, and it puts dockerd
and an SD card into the critical path of a project whose stated promise is
boring technology and minimal dependencies. Worth saying out loud rather than
discovering later. Docker does start at boot (`S99_docker`) and the card is
mounted `noatime`.

## Modbus TCP and the watchdog — the question that gates the swap

`BACKLOG.md` (2026-07-31) made the whole migration conditional on one thing:

> **does the PFC200's Modbus server offer an equivalent output-zeroing
> watchdog?** […] If the answer is yes, the swap is a day.

**Partially. There is a watchdog, and it looks like the wrong kind.**

`/etc/config-tools/modbus_config` configures the Modbus service without
CODESYS. Read 2026-08-19:

```
tcp.enabled  = true      udp.enabled = true
tcp.port     = 502       udp.port    = 502
alternative-watchdog.enabled = false
alternative-watchdog.timeout = 0
alternative-watchdog.options = 4
```

Three things follow, and the middle one is the problem.

1. **A Modbus server is configurable natively.** CODESYS is not required to
   turn it on. Good — the BACKLOG's bad branch ("the whole toolchain is on the
   critical path") is not forced.

2. **The only watchdog on offer is called "alternative", and D-004 chose
   *Standard* on the 750-352 specifically to avoid that behaviour.** Standard
   evaluates a coding mask, so restricting it to `0x8020` (FC6 + FC16) makes
   "watchdog satisfied" mean *outputs are being driven* — which is why
   heatctl needs no separate heartbeat, its per-cycle valve write **is** the
   heartbeat. Alternative resets on any telegram, which D-004 calls "exactly
   backwards": a heatctl that is reading fine but failing to write would keep
   the watchdog fed while the outputs went stale.
   There **is** an `options` mask, currently 4, so the semantics may be
   configurable back toward Standard. **Unverified — this is a hypothesis
   about a name, and names are hypotheses.** Bench-test it before relying on
   it, exactly the way the 750-352's trip test was run on 2026-07-26.

3. **Nothing is listening on 502 today**, because the Modbus server lives
   inside the PLC runtime and no runtime is selected: `get_runtime_config`
   returns empty, `get_possible_runtimes` offers `0 1`, and no CODESYS process
   is running. `/home/codesys/` exists (`CODESYSControl.cfg`, `PlcLogic`) so
   the runtime is installed, just inert.

## The other route: no Modbus at all

`/dev/kbus0` exists and the WAGO DAL libraries are present — `libdal.so`,
`libIoDrvDal.so`, `libIoDrvKbus.so`, `libdbuskbuscommon.so`. So a Linux process
on this box can reach the process image **directly**, with no Modbus server, no
runtime and no CODESYS.

That is what `IOBackend` in `heatctl/backends/base.py` was built for: a third
backend beside `modbus_direct` and `mqtt_io`, and the one where the control↔I/O
link stops crossing a network at all. The 2026-08-08 switch incident — both
Modbus endpoints lost together to a broadcast storm — is the argument for it.

**No SDK headers are on the device** (`find / -name "dal*.h"` is empty), so this
route needs WAGO's SDK or a documented ABI, and it is not a weekend. It is the
better destination, not the first step.

## Mosquitto

Runs as a Docker container `mqtt-broker`, recreated 2026-08-19 from
`/media/sdcard/docker-root/mosquitto/run-broker.sh` — a script rather than a
remembered `docker run`, with the **image pinned by digest** rather than
`:latest`. An unpinned tag means a pull can change the broker under a working
plant, which is the same trap as an unpinned `requirements.txt`.

Config, certs, data and log are bind-mounted from
`/media/sdcard/docker-root/mosquitto/`, so nothing the broker keeps lives
inside the container.

```
allow_anonymous false
persistence true                 # verified: "Restored 2 retained messages"
listener 8883                    # TLS, own CA. The ONLY published port.
listener 1883                    # container network `plc` only, NOT on the host
```

**8883 is the only port exported to the LAN.** 1883 stays on the internal
`plc` docker network for heatctl, which has no TLS support in `mqtt_plane.py`
— so its credentials never cross the wire and it pays no TLS cost on a single
ARM core for traffic that never leaves the box. The 9001 mapping is gone; it
pointed at a listener that did not exist.

Three accounts, each able to write only what it owns:

| user | write | read |
|---|---|---|
| `heatctl` | `heatctl/#`, `homeassistant/#` | `heatctl/#`, `roomtemp/#`, `rtl_433/#`, `sensors/shellies/#` |
| `homeassistant` | `heatctl/set/#`, `heatctl/hp/set/#`, `heatctl/env/#`, `roomtemp/#` | `heatctl/#`, `homeassistant/#`, `sensors/shellies/#` |
| `shelly` | `sensors/shellies/#` | — |

HA deliberately **cannot write heatctl's state topics**. A stale retained value
on `heatctl/temp/...` would be indistinguishable from a live measurement, which
is the failure shape this project keeps meeting. Verified by publishing to each
topic and checking what actually landed — `mosquitto_pub` reports success even
when the broker silently drops on ACL denial, so its exit status proves nothing.

**Permissions gotcha, cost an outage during setup:** `docker exec id` reports
root, but the eclipse-mosquitto entrypoint drops the *main process* to uid
**1883**. Tightening the bind-mounted files to root-owned 0600 made them
unreadable and the broker crash-looped on `Unable to open pwfile`. They are now
owned `1883:1883` with 0600/0700. mosquitto 2.1 also warns that a future
version will refuse a passwd file not owned by root — those two requirements
will collide, and the answer is probably to stop bind-mounting secrets.

Still open: the CA private key was moved off the device to the workstation
(`docs/PFC200.local.md`), so the broker can no longer issue certificates it
presents — but it also means renewals happen off-box.

## The bridge to Home Assistant

Built 2026-08-19. Config in `deploy/pfc200/bridge.conf.template`; the live copy
on the device carries the credential and is 0600 in `config/bridge.d/`.

```
out:  heatctl/#   homeassistant/#   sensors/#
in:   rtl_433/…/WH65B/210/temperature_C     permanent (outdoor contingency)
      rtl_433/…/WH32/245/temperature_C      until Arbeitszimmer gets a Shelly
      heatctl/set/#   heatctl/hp/set/#      dashboard commands
      roomtemp/#   heatctl/env/dew_point    TRANSITIONAL - delete when done
```

Hosted on the PFC rather than on HA deliberately: this side's configuration is
version-controlled, HA's broker configuration is the un-versioned thing
`docs/HA_INTEGRATION.md` exists to compensate for.

**It is a transport change, not an independence gain.** While a room's sensor
still reaches heatctl through HA, that room still depends on HA. What the
bridge buys is that the two migrations — compute onto the PFC, sensors onto
this broker — can happen in either order and one room at a time.

**Narrowed on purpose.** The first version bridged `rtl_433/#` wholesale and
imported 625 retained topics, most of them fossils from 2022. See below; that
is why the inbound leg names two exact topics.

## Retained fossils, and what they were hiding

Bridging `rtl_433/#` pulled a **2022 retained `events` message** onto the PLC
broker, carrying `temperature_C: 13.4` on the very topic that feeds the slab
target — where `UA_ao*(T_set-AT)` makes outdoor the largest single term.

Worse, restarting HA's Mosquitto **replayed that fossil into Home Assistant**,
and `sensor.fineoffset_wh65b_210_t` took it as current: 13.4 °C, last reported
at the moment of the restart, against a genuine 17.3 half an hour earlier.

Which exposed the thing underneath: **the WH65B had gone silent** around
19:34 UTC and the retained fossil was masking it. A dead sensor looked alive
because a broker was remembering 2022 on its behalf. This is the concrete form
of the hazard in "Retained sensor data and staleness detection" in BACKLOG —
retain defeats arrival-time staleness, and here it defeated a human's ability
to notice too.

All retained `rtl_433/#` topics were cleared on both brokers (625 on HA, mostly
years of decoded radio noise from neighbours' meters). Live publishers
repopulate what is live; nothing else should be remembered.

**heatctl was insulated**, and by accident this validated the three-tier
outdoor design: `sensor.heatctl_outdoor_source` reads `forecast`, so the plant
never used either the fossil or the dead station.

## Cutover procedure — and why the source goes off first

heatctl now runs here (2026-08-20). Moving control between machines means a
gap, and the gap is what bites.

**Stop the source first.** When the controller stops, the coupler watchdog
expires after 10 s and zeroes the outputs. The actuators are NC, so they close.
Flow through the heat pump collapses. A *running* compressor then trips
**Er03**, its water-flow fault, which latches — and the unit shuts its own
water pump down with it, so restored flow cannot clear it by itself.

Learned by doing it wrong: the first cutover left the plant unmanaged for about
90 seconds while a missing script was copied across, and Er03 latched eleven
seconds after the new controller started reading fault registers. It cleared itself after
4.5 minutes, matching three self-clears on 2026-08-10.

**Do not read that as tolerance.** Owner: *"Er03 is self clearing if the cause
goes away immediately. It backs off and eventually gets stuck."* The self-clear
is the early part of a retry sequence with a lengthening backoff, so every trip
spends a budget nobody can read and makes the next one likelier to latch for
good — at which point it needs someone on site. See `docs/HEATPUMP.md`.

```
1. Note the current mode.
2. heatctl/set/mode -> off      and WATCH the compressor reach 0 Hz.
3. Stop the losing controller.  ha addons stop local_heatctl
4. Start the winning one.       deploy/pfc200/deploy-heatctl.sh  (SOURCE_STOPPED=1)
5. Restore the mode from step 1.
```

Steps 3 and 4 should still be close together — the valves close either way and
the rooms notice eventually — but with the compressor already off, a slow
step 4 costs comfort rather than a latching fault.

**Single writer.** The App must be *stopped*, not idle. `deploy-heatctl.sh`
checks this from the workstation, which can reach both machines, and fails
closed if it cannot tell.

## The Shelly that already publishes here

`shellyhtg3-9070695AA90C` at `192.168.178.72`, base topic
`sensors/shellies/wohnzimmer`, TLS on 8883 as user `shelly`.

```
sensors/shellies/wohnzimmer/status/temperature:0   {"id":0,"tC":23.7,"tF":74.6}
sensors/shellies/wohnzimmer/status/humidity:0      {"id":0,"rh":62.9}
sensors/shellies/wohnzimmer/online                 true | false     (LWT, retained)
sensors/shellies/wohnzimmer/events/rpc             NotifyFullStatus, NotifyEvent
```

This is a **different device** from the four H&T G3 already in HA. Note the
payload is JSON, not the bare number heatctl's `room_temp_topic` currently
expects — the rtl_433 room reads a bare float. A JSON-extracting topic form is
needed either way.

**Two measured problems with the direct path, both about staleness:**

1. **`wakeup_period` is 600 s and the device deep-sleeps**, despite
   `devicepower:0.external.present = true`. It connects, publishes, disconnects,
   every six minutes observed. Against `room_temp_max_age_s: 900` that leaves
   one missed wake of slack.
2. **Only `online` is retained.** Subscribing while the device sleeps returns
   `online false` and *no temperature*. So a heatctl restart can sit up to a
   full sleep period with no reading for that room and fall back to
   house-average control — silently, which is the failure shape
   `docs/HA_INTEGRATION.md` risk 2 already tracks.

The HA-bridged siblings avoid this with a `/2` heartbeat automation. A
device-direct Shelly has no such helper, which is the honest cost of removing
HA from the path.

**SLEEP CANNOT BE DISABLED, and the reason is physical** (owner, 2026-08-20):
an always-on CPU self-heats and distorts the temperature reading. The device is
accurate *because* it powers down between samples. So "keep it awake" is not a
setting anyone forgot — it is closed permanently, and two mitigations that
depended on it are closed with it:

- **`online` cannot gate freshness.** It is false roughly 357 s in every 360 by
  design. It survives only as a *wake event marker*.
- **Payload timestamps cannot either.** The clock is unset right after wake
  (`"unixtime":null`), which is precisely when a first-message-after-reconnect
  would need it.

What remains is that **room temperature is a sampled signal, ~6 min between
samples**, and the design has to hold that rather than work around it. Options
and consequences are in BACKLOG under "Retained sensor data and staleness
detection"; the one worth building is a normaliser on this box that republishes
retained with an MQTT 5 expiry, so the broker enforces staleness using a clock
we control.

Also: do not mount these where air exchange is poor or near a heat source. The
accuracy depends on the CPU being off.
